# 名簿 DB 新規設計（R1）

**対象**: 名簿4帳（topics / pools / tokens / contracts）と、その判定・検収・評価の全工程
**実装**: [`schema.sql`](schema.sql)（SQLite、検証済み）
**材料**: crypPI registry 設計 v3 とその検証で見つけた欠陥3件、名簿監査（PR #61）の発見、
PR #63 の残作業仕様、ループ統合（REGISTRY_CADENCE）の運用、tx 実体の保持範囲を巡る議論（A/B/C と C′）

既存の JSON 名簿と crypPI v3 の双方を「参考にはするが前提にしない」。
残すものは検証に耐えた考え方だけにし、壊れていた機構は作り直した。

---

## 1. 設計原則（7つ）

1. **事実・判断・検収を分ける**（v3 から継承。書き手がテーブル名で決まる）
2. **NULL は「不明」**。0 や既定値で埋めない（未検証≠不一致、未測定≠不一致、decimals 欠落≠18）
3. **消さない・潰さない**。訂正は行の追加で表現する。多数決で少数派を消さず、
   「競合」は状態として表す
4. **真実には階層がある**。チェーンの確定イベント（Initialize）＞ getter 実測 ＞
   台帳の多数派 ＞ 流れからの推定。低い層が高い層を上書きしない
5. **実体の保持は「引用」で決める**。判定・課題が引用した tx だけをピン留めして持つ。
   引用されていない走査データは再取得可能として外に置く
6. **DB が作業マスター、JSON は輸出形態**。下流（デコーダ・BBC・defi コピー）が
   読む JSON は DB から決定的に生成する。輸出ファイルの履歴は git が持つので、
   DB 内にスナップショット表は持たない
7. **規律は DB が拒否する形で書く**。文章の禁止事項ではなく CHECK・生成列・
   ビューの定義で守る

## 2. 全体構造

```
                        ┌── 輸出（決定的生成）──→ known_topics.json   ┐
   走査・監査・実測 ──→  │                            known_pools.json    │→ BBC / defi
        （run に記録）  │   registry.db（作業マスター）                  │   デコーダ
                        │                            known_tokens.json  │
   LLM / 人間の判定 ──→ │                            known_contracts.json ┘
   人間の検収      ──→  │
                        └── 評価ドメイン（課題・試行・採点、crypPI 用）
```

- 規模感: topics 約7.6千、pools 約6.3千、tokens 約5.6千、contracts 約3百、
  判定は累積でも数万行、証拠 tx は最大で数万件×平均数 KB（圧縮後で数十〜百 MB 級）。
  **SQLite 単一ファイルで十分**。サーバ型 DB が要る規模ではない
- `chain_id` を pools / tokens / contracts の主キーに含める（今は Base のみ。
  横展開＝他チェーンで同じ分析、の受け皿を先に用意する。topics はハッシュ自体が
  チェーン非依存なので持たない）

## 3. ドメイン別

### 3-1. トピック（v3 の骨格を継承し、出口を直した）

事実層（`topic` / `topic_shape` / `topic_signature` / `topic_emitter` /
`topic_evidence` / `topic_flow` / `topic_trap`）は v3 とほぼ同じでよい。
分布や集合そのものが証拠になるもの（形の出現分布、発行元の集合）は、
**集計行として保持する**ことで監査可能にしている（生データが無くても
「20+ 発行元いた」ことは DB 内で数え直せる）。

判断層の変更点は2つ:

- **`topic_verdict` に時刻の UNIQUE を付けない**。最新判定は `id` で決める
- **`verdict_evidence`（判定 × tx × 役割）を新設**。判定の根拠 tx はここで結ぶ。
  v3 の `matched_tx_hash` 1件持ちでは、複数 tx による突合と判定の版管理ができない

検収層の変更点:

- **`topic_review` に代理キー `id`** を持たせ、`finding_issue` から正しく参照する
- **正本ビュー `v_authoritative_topic` は「最新の判定 × 最新の検収」だけで決める**。
  新しい判定が未検収の間は、古い承認済み判定は表に出ない（影に隠れる）。
  下流が古い結論を読み続ける事故を、ビューの定義で防ぐ

### 3-2. プール（v3 から最も変えた部分）

v3 は「ペアを pool 行に直接持つ」設計だったが、監査で分かった現実は
**「ペアの出所によって信頼度が違い、出所同士が喧嘩する」**ことだった
（pool_meta の窓依存 0x0 混入、Initialize との食い違い、同数で決着できない件）。

- `pool` は同一性だけを持つ（アドレス or poolId、種別、状態）。
  アドレスの無い v4 プールを自然に表せる
- ペアは **`pool_pair_assertion`（主張）** として、出所種別と優先度つきで追記する:
  Initialize イベント=100、getter 実測（token0 / getImmutables / slot0）=80、
  pool_meta 多数派=40、旧名簿からの移入=30、流れ推定=10
- 正準ペアはビュー `v_pool_canonical` が最高優先度の主張から決める。
  **最高優先度の中でペアが割れたら `conflicted=1`**。これが「保留10件」の
  機械的な表現であり、保留リストを別管理する手間が消える
- **pool_meta の 0x0 は主張を作らない**。窓の端に出る artifact であって
  ペアの根拠ではない、と監査が確定させたため（観測としては台帳側に残る）
- 「プールではなかった」ものは削除せず `status='not_a_pool'` にして、
  contracts 側へ行を作る。PR #62 の「−53件」は、この状態遷移として表現される
- ネイティブ ETH は `token` 側の番兵行（アドレス 0x0、`is_native=1`）で表す。
  v4 の currency0=0x0 は正規の値であり、「0x0 = 欠落・artifact」と混同しない

### 3-3. トークン

- `decimals` をプールから分離（v3 と同じ判断）。**NULL = 未測定**を守り、
  実測した場合は出所とブロックを残す。新規分の 57.2% が未登録という
  監査結果が、この「埋めない」規律の根拠
- symbol も主張に近い扱いとし、出所を残す（詐称がありうるため）

### 3-4. コントラクト（PR #63 移設仕様の受け皿）

- `contract_role`（役割は複数持ちうる）と **`contract_evidence`** を持つ。
  「プールではない」根拠（token0() の応答、owner() の応答、コード長）を
  機械可読で残す、という移設仕様の要求にそのまま応える
- 移設の完了条件（台帳 legs の残差 0）は、この DB の外の照合だが、
  材料の置き場はこの3表で完結する

### 3-5. tx 実体（C′ の実装）

- 実体は **`tx_payload` に tx_hash 単位で1回だけ**、圧縮 BLOB で持つ
  （receipt が容量の過半を占めるため、無圧縮 JSON は持たない。
  sha256 と展開後サイズを併記して破損を検出できるようにする）
- **ピン留めはトリガで自動化**: `verdict_evidence` か `task_evidence` に
  行が入った時点で、その tx の `pinned` が立つ。保持基準を人の運用に
  依存させない
- 観測サンプル（`topic_evidence`）は自動ではピン留めされない。
  「見た」だけの tx まで抱えると A（全部入り）に逆戻りするため
- 自己完結の範囲は正直に区切る: **tx 単位の根拠（金額照合・構造）は
  自己完結する。集合レベルの判断（多形性・分布・出現極少）は、
  集計行による監査までで、再現はできない**。再現が要る走査データは
  層2として外（台帳・HyperSync 再取得）に置く

### 3-6. リリース

- `registry_release` が4帳の版と輸出 JSON の sha256 を1行に持つ
  （「4帳をそろって更新する」規律の表現。v3 の registry_version を引き継ぎ、
  ハッシュ記録を足した）
- 課題・試行は `release_id` を参照する。**どの版の名簿で測ったか**が
  試行の再現条件の一部になるため（v3 の trial はこれを持っていなかった）

### 3-7. 評価ドメイン（crypPI）

v3 の task / trial / trial_attempt / trial_score を引き継ぎ、1点だけ直す:

- **`trial_score.safe_complete` を生成列にする**。M/P 列から導出される値を
  独立に書けると、列同士が矛盾する行を作れてしまう。生成列なら書けない。
  NULL 伝播により、未判定が1つでもあれば safe_complete は NULL
  （= 完遂とは言えない、fail-closed）になる

## 4. v3 の欠陥 → R1 での修正（検証済み）

| # | v3 の欠陥（実証済み） | R1 の修正 |
|---|---|---|
| 1 | `finding_issue` の FK が rowid 参照で壊れており、FK 強制 ON では topic_review への挿入自体が失敗する | `topic_review` に代理キー。`PRAGMA foreign_key_check` が無出力で通る |
| 2 | `verdict_current` の UNIQUE（topic0, decided_at）が同秒の連続判断を弾き、追記のみの設計と衝突 | UNIQUE を外し、最新は id で決める。同秒2件の挿入が通る |
| 3 | `v_authoritative_topic` が古い承認済み判定を出し続け、1 topic に矛盾する2クラスが返る | 最新判定×最新検収に限定。新判定が未検収なら正本は空（影）になる |
| 4 | DESIGN §3-8 が引用する CHECK が実物に無い（文書と実物の不一致） | 担保は reviewer の NOT NULL と basis の CHECK で実物に明記 |
| 5 | `safe_complete` を独立に書ける | 生成列化し、直接 INSERT はエラーになる |
| 6 | `contract` に役割と証拠が無い | `contract_role` / `contract_evidence` を新設 |
| 7 | trial が名簿の版を持たない | `release_id` を追加 |

## 5. 運用フロー（既存の仕事の受け皿）

- **ループ統合**（3時間サイクル）: 走査を `run(kind='scan')` に記録 →
  新規 topic の事実行を追加 → 判定（LLM/人間）→ 検収 → リリース輸出。
  従来の REGISTRY_CADENCE の手順は「輸出先が JSON ファイル群になる」以外
  そのまま移せる
- **Initialize 批次**（PR #63 残作業1）: HyperSync で Initialize を全件取得し、
  704 件分の主張（priority=100）を投入するだけ。保留10件は
  `v_pool_canonical.conflicted` か主張の有無で機械的に残りが見える
- **known_contracts 移設**（PR #63 残作業2）: 113 件を contract +
  contract_role + contract_evidence として投入する。BBC への輸出は
  従来どおり JSON で行う
- **監査**: finding_issue に消さずに積む。監査の主張は assertion や
  verdict の追加行として反映し、元の行は書き換えない

## 6. 移行（既存 JSON から）

1. 現行4帳を `registry_import`（priority=30）として取り込む。
   取り込み自体を run に記録し、出所を残す
2. pools のキー接頭辞（pair01: / xy: 等）は「登録経路」であって
   プール性の保証ではないことが監査で確定している。移行時に
   接頭辞から status を決めず、全件 candidate として入れ、
   実測済みの分だけ verified に上げる
3. 以後の更新は DB 経由のみ。JSON へは輸出だけが書き、人が直接編集しない

## 7. 入れないと決めたもの

- 走査の生データ全量（層2）。再取得可能であり、DB の仕事ではない
- 台帳そのもの。台帳は BBC のリリース資産として既に管理されている
- スナップショット表。輸出 JSON の履歴は git が持つ
- 秘密情報・API トークン。出所は文字列で参照するだけ
